# T-818 static-ceiling calibration

The public TypeScript `compile(...).workProof` was measured at Platform `660e2300` with the repository default limits. The probe compiled the `definitionRules` of every conformance case that was neither an expected compile refusal, a guard-value case nor a skin case. All 66 selected cases compiled. Their `maximumEvaluationWork` decimal digit counts were: 2 digits in 2 cases, 3 in 4, 4 in 2, 6 in 10, 7 in 20, 8 in 6, 9 in 5, 10 in 1, 11 in 11, 12 in 3 and 14 in 2. The two 14-digit cases are the child-table per-row Compute and per-row parent-reach-out cases. This is a test-corpus distribution, not a sample of released authored rules.

The same public compiler was then measured with a `Compute` expression `missing(var keys)` repeated across 1, 2, 4, 8, 16, 32 and 64 Field cells. The `(maximumResultBytes digits, maximumEvaluationWork digits)` pairs were `(14, 23)`, `(19, 28)`, `(28, 37)`, `(45, 56)`, `(81, 92)`, `(153, 164)` and `(296, 308)`. One Row Compute using `missing(var rowKeys)` under default limits had `(22395, 22411)` digits because a Row Compute may expand to the configured 5,000 graph nodes before an instance supplies rows. The public RuleEngine tests already exercise dynamic Row Compute at default limits in both tiers, so this is an admitted behavior rather than a synthetic invalid definition. The six smaller representative compiler values were pinned and compared across both tiers in [the parity evidence](T-818-work-proof-cross-tier-parity-2026-09-28.md); this larger Row measurement is TypeScript-only diagnostic evidence.

A `10^30` work-unit ceiling would admit all 66 measured corpus cases and one or two dynamic Field cells but refuse four dynamic Field cells and the existing default-limit dynamic Row case. A `10^320` ceiling would admit the measured 64-Field-cell graph yet still refuse that Row case. A ceiling high enough to admit the Row case must exceed a 22,411-digit work proof; its operational meaning has not been established. These observations do not show that the proof is wrong as a conservative upper bound. They show that the current worst-case scalar cannot be used to choose a practical default refusal threshold from the existing corpus alone.

The next T-818 design step is to decide whether to tighten the Row/dynamic proof using a smaller justified reachability bound, state a separate structural dynamic-demand admission policy, or define a per-instance budget after the actual row count is known. The decision must preserve the existing fail-closed runtime step budget and explain which static program property discharges DES-0018 `rules-eng-11` and ledger L271. A numeric ceiling should follow that decision and representative cross-tier measurements. No production behavior, test or mutation result was changed by this probe; T-818 and `kernel-core-ck-7` remain open.

## Recalibration after the demand-depth fix

At Platform `84808745`, the public TypeScript package was rebuilt and the same default-limit `compile(...).workProof` probe rerun. The empty and one-literal cases still report 8 result digits and respectively 1 and 3 work digits. Dynamic Field Compute graphs of 1, 2, 4, 8, 16, 32 and 64 cells still report `(result digits, work digits)` of `(14, 23)`, `(19, 28)`, `(28, 37)`, `(45, 56)`, `(81, 92)`, `(153, 164)` and `(296, 308)`. The one-rule dynamic Row Compute now reports `(301, 316)` rather than `(22,395, 22,411)`, because result-carrying composition is capped at `maxDependencyDepth + 1`. This is a diagnostic of the current TypeScript proof, not new .NET parity or a behavior/mutation certificate.

The earlier `10^320` example now admits the measured Row case, but it permits a worst-case work proof of more than 300 decimal digits and has no demonstrated relation to the runtime `stepBudget` of 250,000 charged operations. A ceiling low enough to express an operational host budget would still reject the supported dynamic Field and Row examples under this proof. The remaining choice is substantive: further prove a tighter semantic transfer, explicitly restrict those authored programs, or define a separate structural admission rule with a justified operational bound. Do not install a scalar limit solely because this recalibration made the Row proof fit under an arbitrary exponent.

## Recalibration after removing dynamic value transfer

The subsequent [presence-only proof change](T-818-dynamic-missing-presence-proof-2026-09-28.md) removes the unsupported result recurrence rather than choosing a ceiling around it. At default limits, the dynamic Row example now has 10 result digits and 25 work digits; dynamic Field graphs of one through 64 cells have 10 result digits and 18 through 22 work digits. Work remains conservative and structurally counted, not a count of runtime budget charges. These values supersede the immediately preceding 316-digit diagnostic for the changed compiler; neither set by itself establishes a safe operational admission threshold.
