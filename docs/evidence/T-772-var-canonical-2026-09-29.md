# T-772 var operand canonicalisation, 2026-09-29

At Platform parent `b0d51d0d` (T-772 core-work pins, PR #194), the scope grammar lowered a `var` whose path operand was not a string in two different ways. TypeScript `grammar.ts` rewrote `{"var":1}`, `{"var":{"cat":["a","b"]}}`, `{"var":[null]}`, `{"var":[]}` and `{"var":""}` to `{"var":"field."}`, a static read of field `""`, and String()-coerced an array's first element (`{"var":[{"cat":…}]}` became field `[object Object]`). The computed operand was dropped from the AST, so the rule read the wrong cell. Reference extraction registered a field `""` (or none) instead of a dynamic read, so the work proof charged it as a static read. .NET `ScopeGrammar.Rewrite` threw an untyped `InvalidOperationException` from `GetValue<string>()` on the same programs, so the two tiers also disagreed.

The contract, from the sources opened:

- Upstream JsonLogic (https://jsonlogic.com/operations.html) reads a numeric `var` as an array index into the data (`{"var":1}` over `["zero","one","two"]` is `"one"`) and `{"var":""}` as the whole data object, which it describes as useful inside `map`, `filter` and `reduce`. The page does not say whether the operand may be a computed expression.
- DES-0018 `rules-ck-7` fixes the addressing grammar as `self`, `field.<name>`, `row.<field>`, `parent.<field>`, `section.<id>.<field>` and `table.<fn>(<col>)`, all named cells. `rules-ck-9` leaves out `map`, `filter`, `reduce` and `merge`, and `rules-ck-8` makes the operator set closed and identical in both tiers. The RuleEngine README states that the grammar is lowered once at publish to a canonical AST.
- The existing corpus already refuses a computed `agg` argument at compile with `rule.compile.bad_grammar` (`aggregate-refusal.json`, Ticket 162), because a reference the graph cannot register statically has no cell.

The profile has no array data context, so the array-index reading has nothing to index, and the whole-data reading exists only for the excluded folds. A computed path cannot be lowered to a canonical cell. The DES and spec together decide the case, and the decision is a compile refusal in both tiers, the same shape as Ticket 162. Allowing a dynamic `var` would add a runtime dependency class the graph does not model for `var`; `missing` keeps its existing dynamic-key support.

The fix is red-first with shared cases in `conformance/hlp.foundation.rule-runtime/corpus/var-operand-refusal.json`. Eight refusals cover numeric, numeric with default, computed, computed with default, `[null]`, `[]`, `""` and a numeric `var` nested in a default. One positive case pins `{"var":["x",7]}` lowering to `{"var":["field.x",7]}` and resolving `7`. Before the change TS failed all eight refusals ("expected a compile refusal and none was raised"). .NET failed all eight: six threw `InvalidOperationException` and the empty cases compiled. Both tiers now refuse with `rule.compile.bad_grammar` in `grammar.ts` `rewrite` and `ScopeGrammar.Rewrite`. The shared runner reports 91 cases PASS with byte-identical canonical values.
