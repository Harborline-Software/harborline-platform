# T-818 representative work-proof parity

The public seams are TypeScript `compile(...).workProof` and .NET `RuleCompiler.Compile(...).WorkProof`. Six representative programs pin decimal values for empty and literal graphs, one and two dynamic Compute cells, an aggregate referenced by a Validate rule, and a Row Compute at two admitted graph nodes. The TypeScript checks passed first. The .NET checks then failed red for the four dynamic programs while empty and literal passed. Result-byte proofs matched in every case; .NET work proofs were smaller. For the one-cell dynamic case, TypeScript expected `11801253547021660190518` and .NET produced `11801248548179722910518`. The other mismatches were two Compute cells (`708074912910306823677470648` versus `708074912900309139802910648`), aggregate Validate (`708148051395913279490506775` versus `708148051385914596247306775`), and two-row Compute (`1416149235951638144053181324` versus `1416149235951303764754941324`).

The cause was one .NET dynamic-cell work transfer using the maximum of dynamic result, aggregate result and input bytes while TypeScript added all three possible conversion and copy inputs. Replacing that maximum with the same sum made all six .NET cases green. The affected TypeScript package passed 350/350 tests, type checking and lint; the affected .NET RuleEngine test project passed 303/303 tests. The shared outcome conformance runner passed 80 cases across the TypeScript reactive and .NET integrity projections. No refactor was needed.

Repository-pinned Stryker.NET 5.0.0 used the RuleEngine source and test projects, the pinned SDK's `MSBuild.exe`, `test-case-filter: FullyQualifiedName~Compiler_pins_public_work_proof_for_cross_tier_calibration`, default coverage analysis, and `mutate: ["**/CoreWorkDerivation.cs{6749..6853}"]`.
