# T-818 static work ceiling

Both rule-runtime tiers now enforce the graph work proof as a static admission ceiling. `RuleEngineLimits` gains `maxStaticWork` (TypeScript `bigint`, .NET `BigInteger MaxStaticWork`, publish-time static), defaulting to `10^26` structural proof units. TypeScript `compile()` and .NET `RuleCompiler.Compile()` throw the existing compile refusal (`CompileError` / `RuleCompilationException`) with the new code `rule.compile.work_exceeded` when `maximumEvaluationWork > maxStaticWork`; a proof equal to the ceiling is admitted. The refusal is graph-level (no rule id) and carries `proof` and `ceiling` as decimal-string params; its message gives the integer factor over the ceiling (omitted for a zero ceiling) and names the host limits and program changes that lower the proof. Both `FormRuleGraph` constructors recompute the proof under their own limits and store the same code through the existing stored-refusal pattern: an admission refusal keeps priority, otherwise every entry point (TypeScript `evaluateInstance`, `reevaluate`, `addRow`, `removeRow`; .NET `EvaluateInstance`, both `Reevaluate` overloads, `AddRow`, `RemoveRow`) fails closed. The 250,000-step runtime budget and the wall-clock ceiling are unchanged. The `interface.yaml` limits block and both corpus loaders carry the limit as a decimal string.

## Calibration

The sweep ran at Platform `a23afe32` before the refusal existed. Each tier's compiler was temporarily instrumented to record `maximumEvaluationWork` for every compile while the whole public test suite ran, and the instrumentation was then removed. The TypeScript run covered the full vitest suite (400 tests, including the 80-case shared corpus) and recorded 354 compiles at default limits; the .NET run covered the RuleEngine test project (305 tests) and recorded 4,383 default-limit compiles. The largest default-limit proof in both tiers is the same 25-digit value, `3,984,532,724,073,286,870,616,000`, from the public dynamic Row Compute graph test. The 64-Field and one-Row dynamic diagnostics measure 22 and 25 digits (`1,631,738,386,921,228,193,152` and `3,983,736,295,385,685,821,324,000`). So `d = 25` in both tiers and the proposal's rule `10^(d+1)` gives `10^26`, unchanged from the proposal.

## Red and green

The tests were written first. `src/__tests__/static-work-ceiling.test.ts` (TypeScript) and `StaticWorkCeilingTests.cs` (.NET) cover the compile boundary at `p = 130` for one literal Compute (admitted at `p`, refused at `p - 1` with exact code, params, null rule id and message), the factor and zero-ceiling message, empty params on other compile refusals, the `10^26` default and the unchanged step budget, the calibration diagnostics and the 25/26 dynamic Row boundary at default limits, graph fail-closed at every entry point at `p - 1` with a normal control at `p`, admission-refusal priority, and a graph that recomputes a one-Row proof over the default ceiling when its own `maxTableRowsPerAggregate` is 200,000 (`984,112,130,658,328,582,132,400,000`). After the minimum compile check and graph refusal, both files passed. They match in both tiers, but because the proof itself did not change they pass before and after and are parity evidence, not red-first tests.

With the compile throw disabled, the refusal case failed in both tiers (TypeScript `expected a compile refusal and none was raised`; .NET the corpus case and `Emit_cross_tier_artifact`), then passed with it restored.
